Эти команды устанавливают, запускают, проверяют, ремонтируют и обновляют локальный прокси
easyproxy и его интеграцию с Codex.

## Настройка

### `epx init` · `epx setup`

Интерактивный мастер настройки (`setup` — alias команды `init`). Он спрашивает провайдера
(preset или custom), API-key (буквально или `${ENV}`), модель по умолчанию и порт прокси,
сохраняет `~/.easyproxy/config.json`; при желании внедряет прокси в
`$CODEX_HOME/config.toml` (по умолчанию `~/.codex/config.toml`) и при необходимости
устанавливает shim автозапуска Codex.

## Жизненный цикл прокси

### `epx start [--port <port>] [--socks5 [host:port] | --socks5-off]`

Запустить proxy server (предпочтительный порт `10100`). При запуске пишется состояние
PID/runtime-port, а попытка поднять второй живой экземпляр отвергается. Если предпочтительный порт
занят, `start` проверяет, кто его удерживает, и в любом случае останавливается: он отказывается от
запуска, если там отвечает easyproxy, а иначе сообщает о неопознанном владельце порта. Прокси
никогда сам не переносит listener на другой порт, поскольку тогда первый прокси продолжил бы
работать, а Codex был бы перенаправлен на второй. Явно указанный другой `--port` также отклоняется
при общем `EASYPROXY_HOME`: режим наблюдения и режим с лимитами оба пишут в один журнал расходов.
Для независимого соседнего экземпляра используйте отдельный `EASYPROXY_HOME`; `port: 0` поручает
ОС выбрать только порт и не разделяет состояние. На старте прокси синхронизирует модели каждого
провайдера в каталог Codex. При shutdown он восстанавливает native Codex — если только прокси не
был запущен как managed service (`EPX_SERVICE=1`). Соседний экземпляр, запущенный рядом с уже работающим
прокси, не делает ни того, ни другого, в том числе при остановке через `epx stop` или сигналом: он
обслуживает только прямые запросы на своём порту, а Codex, Grok и Claude остаются направленными на
прокси, который уже работал.

`--socks5` (по умолчанию `127.0.0.1:10808`) сохраняет SOCKS5 URL в `config.proxy` и направляет
исходящие HTTP(S)-запросы через настоящий SOCKS5-туннель. `--socks5-off` удаляет только сохранённый
SOCKS5-прокси и не удаляет HTTP-прокси. Значение переживает `epx update`, поскольку хранится в
конфигурации, а не в установленном пакете. Имя пользователя и пароль можно указать в URL, но в
startup-логах они скрываются.

```bash
epx start
epx start --port 8080
epx start --port 10100 --socks5
epx start --socks5-off
```

### `epx stop`

Link Child без супервизора при сигнале восстанавливает нативный Codex и управляемый Grok до закрытия listener, проверяя подключение перед каждой записью. Сервис/Desktop, sibling, передача перезапуска и квитанция stop родителя сохраняют настройки. Во время завершения перезапуск возвращает `409 runtime_stopping`. Принудительное завершение может обойти сигнал; восстановление родителем `epx stop` остаётся необходимым.

Остановить работающий прокси (по PID) и удалить PID-file; для автономного владельца также восстановить native Codex. Если
установлена managed background service, `epx stop` сначала останавливает и её, чтобы она не
перезапустила прокси обратно. Рычаг прокси в боковой панели веб-дашборда, потянутый до упора вниз, выполняет то же действие (`POST /api/stop`) на всех бэкендах, кроме планировщика заданий Windows: там обёртка может перезапустить прокси после завершения задачи, поэтому дашборд отказывает с `respawnable_service`, ничего не меняет и просит выполнить `epx stop`.

На подключённом клиенте hub команда `epx stop`, включая успешную остановку через API, сохраняет принадлежащие соединению маршрутизацию Codex, каталог моделей и конфигурацию Grok. `epx start` снова обслуживает их, не внедряя маршрутизацию заново. Чтобы вернуть Codex к собственному аккаунту, выполните `epx disconnect`; для повторного применения уже восстановленной нативной маршрутизации используйте `epx sync --restart-codex`.

Явная остановка Remote Link Child при успешном восстановлении общей конфигурации восстанавливает нативную маршрутизацию Codex, каталог и сохранённые в резервной копии метаданные истории возобновления, а также удаляет управляемую конфигурацию Grok. Сохранённое соединение с Home остаётся; удалить его можно командой `epx disconnect`. Чтобы снова использовать Home из Codex, выполните `epx start` (или `epx service start` для установленной службы), затем `epx sync --restart-codex`. Один запуск не применяет маршрутизацию заново; sync не создаёт блок Grok повторно.

Если владение соединением нельзя подтвердить до остановки службы, API остановки возвращает HTTP 409 с `sharedTeardown: "refused"`, оставляя прокси и менеджер службы работающими. Дождитесь завершения подключения или отключения и повторите попытку.

При остановке подключённого клиента команда сверяет доказательство идентичности слушателя с защищённой локальной записью рантайма. Это требуется и для клиентского слушателя, и для обычного прокси; обычный прокси также должен подтвердить сохранение настроек через аутентифицированный запрос чтения. Старые или непроверенные рантаймы отклоняются до остановки службы или процесса. Обновите и перезапустите рантайм через управляющий супервизор, затем повторите команду.

Для уже остановленного клиента команда подтверждает неактивность службы и отсутствие рантайма на известных локальных адресах, затем возвращает обычный результат «не запущен».

### `epx restart`

Если прокси уже работает, команда запрашивает перезапуск на месте у точно аттестованных PID и
порта, ждёт штатного drain и проверяет появление другого runtime PID на том же порту. Управляемая
маршрутизация и supervision службы сохраняются; неопределённый результат запроса не повторяется как
отдельный stop/start. Если прокси не запущен, используется обычный запуск через `ensure`.
Если работающий слушатель нельзя подтвердить привязкой к runtime PID (включая прокси до обновления),
перезапуск завершается безопасным отказом без `ensure` или stop/start. После проверки владения
выполните `epx stop`, затем один раз `epx start`.

### `epx ensure`

Идемпотентно убедиться, что фоновый прокси запущен, а затем синхронизировать его живой каталог
моделей. Если `codexAutoStart` равен `false`, команда сообщает, что автозапуск отключён, и ничего
не делает.

### `epx restore [back]` · `epx eject [back]`

Восстановить native Codex **без** остановки прокси — удалить внедрённые строки конфигурации и
маршрутизируемые записи каталога, чтобы обычный `codex` снова работал нативно. `eject` — alias
команды `restore`.

Восстановленный каталог исключает снятые нативные модели, включая `gpt-5.3-codex-spark`,
как с bare ID, так и с доверенным префиксом аккаунта. Это действует с резервной копией и без неё;
исходная копия и сохранённые пользователем прежние настройки выбора моделей остаются нетронутыми.

Передайте `back`, чтобы любая из этих форм снова направила обычный `codex` на уже запущенный
прокси, не меняя жизненный цикл самого прокси:

```bash
epx restore back
epx eject back
```

### `epx recover-history --legacy-openai --yes`

Явное восстановление для старых development-сборок, которые переназначали историю Codex App ещё
до появления обратимого backup-механизма. Если база истории Codex заблокирована, сначала
закройте Codex.

Это широкое и разрушительное переименование: все треды с пользовательским сообщением, которые
сейчас помечены `easyproxy`, меняются на `openai`, `exec` нормализуется в `cli`, а event marker
устанавливается. Корректная история выделенного провайдера тоже входит в охват. Сначала сделайте
резервную копию и запускайте команду только если нужен весь этот охват.

### `epx recover-history --epx-compaction <thread-id> --yes`

Исправьте историю одной задачи, сжатой через маршрутизируемого провайдера, перед её возобновлением в нативном Codex. Команда выбирает ровно одну задачу по UUID, сначала сохраняет приватную побайтовую резервную копию, а затем преобразует только принадлежащее easyproxy состояние сжатия `epx1:`/`epx2:` в обычную сводку, которую может воспроизвести нативный Codex. Нативное зашифрованное содержимое и другие задачи не изменяются. Перед запуском закройте выбранную задачу; если rollout изменится во время обработки, восстановление остановится без замены файла.

### `epx uninstall` · `epx remove`

Остановить службу и прокси, удалить службу и Codex shim, восстановить native Codex, а затем
удалить локальную конфигурацию easyproxy только если все шаги восстановления завершились успешно.
`remove` — alias команды `uninstall`. Очистка конфигурации требует ownership metadata, созданных
при свежей установке; legacy- или shared-directory остаются на месте.

Когда `epx uninstall` запускается от root или из Windows-консоли с повышенными правами (администратора),
команда сначала проверяет, что никакая другая учётная запись не может изменить каталог конфигурации,
каталоги над ним и любые каталоги внутри него, а также что ни одна ссылка внутри каталога конфигурации
не ведёт за его пределы (в Windows — что ссылок в нём нет вовсе). Если хотя бы одна проверка не проходит, удаление останавливается до каких-либо
изменений и сообщает причину. Запустите `epx uninstall` от учётной записи, которой принадлежит каталог
конфигурации, без `sudo` и прав администратора, или ограничьте эти каталоги этой учётной записью и
удалите такие ссылки, затем запустите команду снова. На Windows ARM64, где easyproxy не может определить,
повышены ли права, действует та же проверка; если её нельзя выполнить, остановите easyproxy и удалите
каталог конфигурации вручную.

Записанный элемент, родительский каталог которого внутри каталога конфигурации является ссылкой
(символической ссылкой или junction), остаётся на месте и выводится как оставшийся путь, а запуск
завершается частичным удалением. Замените эту ссылку настоящим каталогом или удалите её, затем снова
запустите `epx uninstall`, чтобы завершить удаление.

## Status и health

### `epx status [--json]`

Status и `epx doctor` сравнивают версии текущего CLI и работающего прокси. Если CLI новее,
перезапустите прокси из нужной актуальной установки. Для фоновой службы используйте
`epx service restart`. В macOS рассинхронизация версий оставляет определение службы байт-в-байт неизменным, поэтому `epx service repair` ничего не перезагрузит и старый процесс продолжит обслуживание. Если новее прокси, обновите CLI
или исправьте `PATH`, чтобы он указывал на нужную установку. Диагностика не ремонтирует службу
и не меняет разрешение запросов.

При одинаковых строках версий, значениях `unknown` / `0.0.0` или отсутствии версии прокси
предупреждение подавляется. Doctor не считает placeholder подтверждённым совпадением.
Разные строки, которые нельзя строго разобрать как SemVer, и версии, отличающиеся только
build metadata, вызывают нейтральное предупреждение без указания устаревшей стороны.
Пробелы не удаляются, префикс `v` не нормализуется. JSON содержит ту же рекомендацию в
`versionSkew` с прежними полями `cliVersion`, `proxyVersion`, `skewed` и `warning`.

Печатает read-only диагностическую сводку: PID прокси, достижимость `/healthz`, URL дашборда,
путь к конфигу, провайдера по умолчанию, настройку автозапуска Codex, состояние службы, состояние
shim'а и redacted effective Codex home. Только явная и высокоуверенная сигнатура mismatch
runtime-home Windows Orca даёт actionable-warning о несоответствии App-home; `CODEX_HOME`
автоматически при этом не меняется.

В текстовом выводе после сводки OAuth-logins также присутствует блок **OAuth health**:
`OAuth health: ok`, если все известные аккаунты здоровы, либо `OAuth health: warning` с одной
redacted-строкой на каждый нездоровый аккаунт (провайдер, замаскированный id аккаунта, статус
вроде reauthentication required, rate/quota limited или refresh conflict) плюс необязательная
подсказка `Action:`. Идентификаторы маскируются; токены и email никогда не печатаются. В
контракт `--json` этот health-блок пока не входит.

```bash
epx status
epx status --json
```

Сокращённая форма JSON:

```json
{
  "schemaVersion": 1,
  "proxy": {
    "running": false,
    "pid": null,
    "health": {
      "ok": false,
      "url": "http://127.0.0.1:10100/healthz",
      "message": "unreachable"
    }
  },
  "dashboard": {
    "url": "http://localhost:10100/"
  },
  "paths": {
    "config": "/Users/example/.easyproxy/config.json",
    "pid": "/Users/example/.easyproxy/epx.pid",
    "runtime": "/path/to/bun"
  },
  "runtime": {
    "source": "bundled"
  },
  "codexHome": {
    "effectiveCodexHome": "C:\\Users\\[USER]\\.codex",
    "appCodexHome": "C:\\Users\\[USER]\\.codex",
    "mismatch": false,
    "warning": null,
    "action": null
  },
  "codexAutostart": true,
  "defaultProvider": "openai",
  "service": {
    "summary": "not installed (logs: /Users/example/.easyproxy/service.log)"
  },
  "codexShim": {
    "summary": "Codex autostart shim: not installed"
  }
}
```

Реальный объект также включает `listen` (порт, hostname, источник runtime/config), диагностику
загрузки конфига и диагностику bundled-plugin'а Codex. JSON-schema только расширяемая: новые
версии могут добавлять поля, но существующие должны оставаться стабильными. Она намеренно не
включает API-key'и, OAuth-token'ы, заголовки авторизации, содержимое запросов, email и
идентификаторы аккаунтов.

Чтение отчёта работающего прокси ожидает завершения ограниченной по времени диагностики службы: до 6,5 секунды на macOS/Linux и до 16,5 секунды на Windows, если кэш диагностики пуст или устарел. Чтение из кэша возвращает результат без такого ожидания. При тайм-ауте по-прежнему используются локальные диагностические данные; успешная проверка `/healthz` сама по себе не подтверждает защиту при перезапуске.

### `epx health [--json]`

Identity-check живого прокси. Текстовый вывод сообщает PID/порт; `--json` отдаёт
`{ok, pid, port}`. Команда завершается кодом 0 только когда прокси здоров, и 1 во всех остальных
случаях, поэтому подходит для service probe.

### `epx ready [--json] [--wait [--timeout <seconds>]]`

Проверяет готовность после синхронизации через не требующий аутентификации `GET /readyz`. При
готовности возвращается `200`; для `pending` и терминального `failed` возвращается `503` с
`Retry-After: 1`. Санитизированные поля HTTP-ответа: `{service, version, uptime, pid, port, status, protocol, minimumClientProtocol, managementUrl, features}`. `protocol` — текущая версия удалённого протокола hub, `minimumClientProtocol` — минимальная совместимая версия клиента, а `managementUrl` — канонический origin управления для браузера.
Старые прокси без `/readyz` fail-closed как `unreachable`; `/healthz` — отдельная проверка liveness,
а не готовности. По умолчанию команда выполняет одну пробу. `--wait` опрашивает до готовности или
тайм-аута, но при терминальном `failed` завершается немедленно. Тайм-аут по умолчанию — 45 секунд;
`--timeout <seconds>` требует `--wait` и принимает целые положительные значения 1–300 секунд. CLI JSON выдаёт
`{ready, status, pid, port}`, где `status` — `ready`, `pending`, `failed` или
`unreachable`. Коды завершения: 0 — готово; 1 — не готово, pending, failed, тайм-аут или
недоступность; 64 — недопустимые аргументы.

Если при запуске прокси появляется сообщение, что домашний каталог Codex не найден, запустите Codex один раз или укажите в `CODEX_HOME` каталог, уже инициализированный Codex. Затем выполните `epx sync`. Успешная синхронизация восстанавливает маршрутизацию, но статус `failed` по-прежнему отражает результат запуска текущего процесса. Перезапустите прокси и проверьте новый процесс командой `epx ready`.

Для службы, установленной через CLI, используйте зарегистрированные значения `CODEX_HOME` и `EASYPROXY_HOME`. Если эти пути отсутствуют в старом определении службы, один раз выполните `epx service repair` с этими настройками. При необходимости инициализируйте каталог Codex, выполните `epx sync` и перезапустите службу. Прокси под управлением настольного приложения перезапускайте из приложения.

Чтобы перевести службу CLI на другой существующий каталог Codex, выполните `epx service uninstall` с исходными настройками. Если служба удалена, но восстановить штатную конфигурацию Codex не удалось, устраните указанную ошибку и выполните `epx restore` с теми же настройками.

Если в Windows после неудачного восстановления осталась запись о незавершённой очистке, перед сменой каталогов выполните `epx stop` из установки, которой принадлежала служба, с исходными путями. Пока запись существует, `epx update` откажется заменять пакет.

После успешного удаления и восстановления сохраните `EASYPROXY_HOME`, выберите новый `CODEX_HOME` и выполните `epx service install` с прежним бэкендом и параметрами. С новыми настройками выполните `epx sync` и проверьте готовность командой `epx ready`. При сбое запуска следуйте описанным выше шагам восстановления.

### `epx doctor`

Запускает read-only диагностику среды и связности: пути состояний и тип файловой системы,
двойные установки WSL, proxy environment/config, достижимость ChatGPT, предупреждения о plugin'е
и project-config Codex, а также ожидающую миграцию истории. Раздел, касающийся app-home Codex,
тоже обнаруживает узкий mismatch runtime-home Windows Orca и при необходимости объясняет миграцию
службы. Пути в этом выводе маскируют имя пользователя ОС. Doctor печатает подсказки по ремонту,
но ничего не меняет.

Раздел **OAuth reliability** показывает, можно ли записывать credential storage, удаётся ли
создавать refresh single-flight/lock file'ы в `EASYPROXY_HOME`, есть ли нездоровые OAuth- или
Codex-pool-аккаунты (с masked-id) с подсказкой `Action:`, а также статическое OK-подтверждение,
что путь Codex forward не подделывает metadata официального клиента. Doctor никогда не мутирует
credential'ы и не выполняет repair.

## Синхронизация каталога

### `epx sync [--expect-link <linkId> | --expect-hub-key <apiKeyId>] [--local-only] [--json] [--restart-codex] [--restart-app-server-only] [--child <linkId>]... [--restart-children[=app-server] | --restart-children=codex --yes]` <span id="epx-sync---restart-codex---restart-app-server-only"></span>

На Home Remote Link после успешной фиксации актуального каталога `epx sync` также синхронизирует подходящие связанные дочерние машины. `--local-only` отключает эту рассылку. `--json` выводит один документ `epx.sync.fanout/1` с результатом Home и состоянием каждой дочерней машины; для пропущенной машины указана причина. Ненулевой код выхода самого Home возвращается без изменений. Если Home завершился успешно, пропуск синхронизации подключённой дочерней машины, её сбой или тайм-аут либо недоступное хранилище связей дают код выхода 6. Преднамеренные пропуски, включая связи, созданные клиентом, и `--local-only`, сохраняют прежнее поведение; пропущенная подключённая машина получает подсказку `hint`. В текстовом режиме сообщение о недоступном хранилище не содержит путь. Код 7 зарезервирован для выполняющегося обновления. Если синхронизация Home выбрасывает исключение в режиме JSON, stdout по-прежнему содержит один документ результата, а stderr — безопасно отформатированную диагностику. Связи, исключённые через `--child` (`not-selected`), и дочерние машины, занятые операцией Child (`child-busy`), тоже считаются преднамеренными пропусками и не дают кода 6. Запрошенный перезапуск дочерней машины, который достоверно не произошёл, даёт код выхода 6.

Рассылка не запрашивает перезапуск Codex на дочерней машине, если не передан `--restart-children` (процессы app-server) или `--restart-children=codex --yes` (приложение Codex Desktop: это завершает живые разговоры и требует сеанса рабочего стола с выполненным входом на той машине). Home сначала синхронизирует каждую выбранную дочернюю машину, заново считывает её активность и только затем отправляет перезапуск второй закреплённой синхронизацией. Он пропускает перезапуск, но не синхронизацию, для дочерней машины, которая в этот момент ретранслирует запрос к модели (`restart-skipped:link-active`) или чью активность не удалось прочитать (`restart-skipped:activity-unknown`), для дочерних машин Windows (`restart-skipped:windows`) и для `epx-child` (`restart-unsupported:epx-child`), после чего завершается с кодом 6. Связь, тип дочерней машины которой не записан, всё же получает флаг перезапуска во второй синхронизации: так Home узнаёт, что там работает `epx-child`, который этот флаг игнорирует. Если перезапуск не удалось отправить или он отправлен, но его результат неизвестен, строка дочерней машины содержит `restart-not-run` или `restart-result-unknown`, и код выхода также 6. Как и для `epx link restart-codex`, эта защита работает по возможности: запрос, начавшийся между чтением активности и перезапуском, всё ещё может быть прерван. `--child <linkId>` (можно повторять) ограничивает рассылку этими связями; остальные получают `not-selected`. Дочерняя машина, занятая операцией Child, например `epx link update`, пропускается как `child-busy`. Закреплённая синхронизация дочерней машины всё же может перезапустить её собственный клиентский рантайм EasyProxy после применения изменённых настроек Home. Если Home завершит локальный процесс SSH по тайм-ауту, уже начатая удалённая синхронизация может продолжиться на дочерней машине.

> **Дочерняя машина Remote Link:** на полном Child с `epx` команда `epx sync` также применяет настройки Codex с Home и перезапускает клиентский рантайм, если он запущен раньше применения; при сбое перезапуска прежний рантайм продолжает работать, а команда завершается с ненулевым кодом. На легковесном хосте `epx-child` команда `epx-child sync` запускает `epx-child serve`, если ретранслятор отсутствует, перезапускает его при `runtimeStartedAt < lastApplyAt` и отправляет отчёт о паритете по принципу best-effort вне режима `stale` (при сбое смены прежний ретранслятор останавливается и команда завершается с ненулевым кодом, а приложение Codex Desktop и долгоживущие процессы `app-server` при необходимости перезапускаются отдельно). Поля `epx status --json` (или `epx-child status --json`) на Child и `epx link status --json` на Home описаны в разделе [Remote Link apply parity](/reference/cli/lifecycle/#remote-link-apply-parity) (на английском). На Home команда `epx link check (--link-id <id> | --all)` считывает установленную версию и путь обновления каждого Child, добавленного с Home, через `epx update --plan` по SSH (60 секунд на Child, установка не меняется), а `epx link status --json` добавляет к каждой строке блок `child`; см. [Child install, catalog and activity](/guides/remote-link/#child-install-catalog-and-activity) (на английском). `epx link sync`, `epx link restart-codex --yes` и `epx link update --yes` запускают на этих Child задания синхронизации, перезапуска Codex и обновления и выводят документ `epx.link.child-job/1`; см. [Operating Children from the Home](/guides/remote-link/#operating-children-from-the-home) (на английском). `epx link policy` читает или меняет политику Child на Home; автоматическая рассылка каталога включена по умолчанию и после изменения каталога Home синхронизирует подходящие Child по SSH; см. [Automatic catalog fan-out and the Child policy](/guides/remote-link/#automatic-catalog-fan-out-and-the-child-policy) (на английском).

Явно запрошенный перезапуск также выполняется после успешного сохранения изменения `config.toml`, даже если байты каталога и кэша не изменились. Операция только с конфигурацией без изменений, отказ, предварительная проверка или отменённая запись не вызывают перезапуск. Без флага перезапуска sync никогда не перезапускает Codex автоматически.

Получить живой список моделей от каждого настроенного провайдера и заново внедрить объединённый
каталог в Codex. Запускайте после добавления провайдера или когда нужно обновить доступные
модели.

Если всё ещё работают долгоживущие процессы Codex `app-server`, `epx sync` предупредит, что они
могут продолжать отдавать старый in-memory список моделей, хотя файлы
`easyproxy-catalog.json` / `models_cache.json` уже обновлены. Передайте `--restart-codex`, чтобы
перезапустить подходящие процессы `codex … app-server` и `codex-code-mode-host` **и** полностью
закрыть и заново запустить Desktop-приложение Codex на macOS, Linux и Windows, чтобы model
picker перечитал каталог. Живые conversation'ы при этом завершаются. Широкий
`pkill -f codex` намеренно не используется.

`--restart-desktop-app` — устаревший alias `--restart-codex`. Он по-прежнему работает, печатает
предупреждение об устаревании и не ограничен Windows.

`--restart-app-server-only` возвращает прежнее узкое поведение: `SIGTERM` только подходящим
процессам app-server / code-mode-host текущего пользователя, Desktop-приложение остаётся
запущенным (активные turn'ы всё ещё могут оборваться). Если флаг указан вместе с
`--restart-codex` или `--restart-desktop-app`, побеждает узкий scope: потеря живых
conversation'ов невосстановима, а устаревший picker — нет.

Если команда запущена изнутри приложения Codex, restart передаётся detached helper'у, и эта
сессия завершается вместе с приложением.

**Синхронизация с закреплённым источником.** `epx sync --expect-link <linkId>` (Remote Link Child) и `epx sync --expect-hub-key <apiKeyId>` (клиент hub) выполняют синхронизацию, только если эта машина всё ещё подключена к этой связи или с этим ключом. Иначе ничего не меняется, локальные провайдеры не синхронизируются, команда завершается с кодом 5, а последняя строка stderr — `{"phase":"child_link_mismatch"|"hub_client_mismatch","reason":...}`. Неверный или повторённый флаг завершает команду с кодом 2. Подробнее: [английская справка](/reference/cli/lifecycle/#sync-only-from-the-expected-home---expect-link-and---expect-hub-key).

### `epx sync-cache [--restart-codex] [--restart-app-server-only]`

Инвалидировать локальный кэш model picker'а Codex, чтобы он пересобрался из активного каталога
easyproxy. Предупреждение о stale-`app-server` и те же optional restart-флаги работают так же, как
и у `epx sync`.

### `epx catalog pull <https-url> [--auth-env <NAME>] [--json] [--restart-codex] [--restart-app-server-only]`

Устанавливает полный каталог, который отдаёт эндпоинт `/v1/catalog` другого экземпляра EasyProxy,
и затем синхронизирует `models_cache.json`. URL должен быть HTTPS; HTTP допускается только на
loopback. Учётные данные в URL, query, фрагменты, редиректы, слишком большие ответы и невалидные
каталоги отклоняются до любой локальной записи. Аутентификация необязательна и читается только по
имени переменной окружения (`--auth-env`), но не из argv.

HTTP-запросы к loopback отклоняются до добавления заголовков аутентификации и отправки запроса, если применяется `HTTP_PROXY` или `http_proxy`, а в `NO_PROXY` или `no_proxy` нет подходящего исключения. `ALL_PROXY`/`all_proxy` и настройки только `HTTPS_PROXY`/`https_proxy` не вызывают это ограничение для HTTP; получение каталогов по HTTPS остаётся разрешённым. Сообщение об отказе не содержит адрес прокси или токен аутентификации. Непустые значения `http_proxy` и `no_proxy` имеют приоритет над `HTTP_PROXY` и `NO_PROXY` соответственно. Для совместимых с Bun правил обхода прокси используйте имена хостов, совпадающие записи `host:port`, IPv6-адреса в квадратных скобках, например `[::1]`, или `*`; не используйте URL, пути или префикс `*.`.

Каталог и кэш пишутся под общей блокировкой каталога Codex; при сбое сохраняются last-known-good
файлы. Идентичные байты — это no-op, сохраняющий mtime. `--restart-codex`,
`--restart-app-server-only` и устаревший alias `--restart-desktop-app` здесь означают то же, что
у `epx sync` и `epx sync-cache`, и применяются только после реальной записи. Условные запросы
`ETag` в эту команду не входят. Полная `--json`-обёртка и коды выхода описаны в
[английской справке](/reference/cli/lifecycle/).

## Фоновая служба

### `epx service [install|repair|restart|start|stop|status|uninstall|remove]`

Запустить easyproxy как login-managed background service (macOS **launchd**, Linux **systemd user
unit**, Windows **Task Scheduler**), которая автоматически стартует при логине и сама
перезапускается при crash. Запуски службы выставляют `EPX_SERVICE=1`, чтобы restart не дёргал
конфиг Codex.

При установке через Windows Task Scheduler используется обычный приоритет процесса (`Priority=4`).
Прежний фоновый приоритет (`7`, также значение планировщика по умолчанию при отсутствии параметра)
при конкуренции за CPU может задерживать ответы проверки состояния: трей показывает Offline, хотя процесс работает.
После обновления выполните `epx service repair`, чтобы изменить этот зарегистрированный приоритет и перезапустить службу.
Может потребоваться подтверждение UAC. Если уже задан обычный или высокий приоритет, сам приоритет не вызывает перерегистрацию.

В Linux systemd-юнит вызывает первый обычный исполняемый файл `epx`, найденный в `PATH` на момент
установки, а не пути Bun и CLI внутри установленного дерева пакета. Менеджеры версий вроде **mise** и
**asdf** устанавливают в каталог с версией и удаляют старый при обновлении; их стабильный shim
сохраняет разрешение юнита. Исходные checkout'ы без launcher'а `epx` сохраняют прямую форму Bun + CLI.
Доверенный `EASYPROXY_BUN_PATH`, выбранный до запуска Bun, сохраняется через shim; пути к Bun,
поставляемому внутри пакета, перенаходятся после обновлений.

В macOS launchd, напротив, использует пути Bun и CLI внутри пакета, выбранные при install или repair.
Это не даёт изменяемому PATH-shim получить service API token и настроенное окружение прокси при
последующем restart. После обновления установки через менеджер версий выполните `epx service repair`,
чтобы обновить эти пути перед перезапуском службы.

Агент macOS использует `ProcessType=Interactive`, чтобы избежать ограничений CPU и I/O стандартного класса daemon и сохранить отзывчивость проверок состояния под нагрузкой. После обновления существующей установки выполните `epx service repair`, чтобы применить и эту политику.

Неподтверждённая загрузка определения остаётся ожидающей между вызовами repair, даже после смены токена. Регистрация повторяется только при доступной начальной проверке launchd; может потребоваться графический сеанс входа. Любая успешно созданная исходная резервная копия сохраняется до принятого bootstrap и проверки соответствующего задания. Создание копии выполняется по возможности; у новой установки нет предыдущего определения.

Если начальная проверка launchd недоступна, repair отказывается до записи нового plist или резервной копии. Если bootstrap изменённого определения отклонён, а состояние доступно для проверки, repair пытается восстановить прежнее определение. Если проверка сразу после bootstrap не может прочитать состояние, повторное удаление задания и восстановление не выполняются: принятый bootstrap даёт предупреждение о неподтверждённой перезагрузке, отклонённый завершается ошибкой. Для неизменённого определения успешный восстановительный kickstart с последующей недоступной проверкой всё ещё может привести к повторному удалению задания. Перед повторной попыткой выполните `launchctl print gui/$(id -u)/com.easyproxy.proxy`. Новая установка удаляет осиротевшие файлы восстановления; полное удаление убирает их даже без plist. Очистка файлов восстановления новой установки, удаление маркера ожидания и очистка при удалении игнорируют только уже отсутствующие файлы. Остальные ошибки этих шагов сообщаются как сбой без удаления состояния установки. После проверенного repair и записи состояния удаление резервной копии `.prev` выполняется по возможности; его ошибка не меняет успешный результат repair.

Определения, установленные до этого изменения, по-прежнему содержат старые версионные пути и не могут
мигрировать сами — после удаления старого исполняемого файла ни один код easyproxy уже не запустится,
чтобы это исправить. Выполните `epx service repair` один раз после обновления. После этого запуски
службы в Linux следуют за launcher'ом, а repair в macOS записывает новые пути пакета в определение
launchd. Уже работающий прокси внешним обновлением не заменяется: если установленный CLI новее
работающего прокси, выполните `epx service restart`, чтобы обслуживалась новая сборка. В macOS здесь
`repair` недостаточно: определение не изменилось, а repair, который ничего не меняет, ничего не
перезагружает. Если новее прокси, проверьте установку CLI и `PATH`, как описано в
[`epx status`](#epx-status---json).

```bash
epx service
epx service install
epx service repair
epx service restart
epx service status
epx service uninstall
```

На Windows bare `epx service` выполняет путь установки только после того, как отсутствие подтверждено и для Task Scheduler, и для WinSW. Если любой из запросов статуса не даёт определённого ответа, он отказывается что-либо регистрировать и предлагает выполнить `epx service status`; явный `epx service install` используйте только после подтверждения отсутствия.

На Windows `epx service status` отдельно показывает регистрацию в Task Scheduler и
identity-проверенную достижимость прокси EasyProxy. Он не печатает локализованную таблицу
`schtasks`, чтобы сводка оставалась читаемой на любых code page Windows.

На Windows создание записи в Task Scheduler требует elevation. Когда распознан локализованный
текст access-denied, остаётся прежний путь guidance. Если текст неразборчив, fallback использует
владение command-shape `/create /tn easyproxy-proxy /xml <non-empty-path> /f`, status 1 и
подтверждённый non-elevated token; после этого действие Startup Safety в дашборде может само
запросить UAC. Если fallback не смог определить состояние token'а, он оставляет исходную
scheduler-error. Чужие задачи и чужие операции никогда не получают automatic-elevation marker.
Либо подтвердите UAC через дашборд, либо заново выполните `epx service install` в elevated
окне PowerShell.

Если при запуске выводится `another process owns the runtime mutation lease` или `epx service status` показывает `Runtime mutation lease busy`, аренда блокирует запуск или изменения службы, даже если прокси не запущен. Сообщение содержит путь к блокировке, записанный PID, жив ли этот PID сейчас, имя исполняемого файла, если его удалось получить, и возраст аренды. Подлинность процесса не проверяется: PID мог быть переиспользован, поэтому состояние и имя исполняемого файла относятся к процессу, который занимает этот PID сейчас. Дождитесь завершения операции и повторите попытку; не удаляйте блокировку и не останавливайте процесс, опираясь только на этот PID. Последующая попытка изменения может забрать устаревшую аренду, когда её возраст превысит 30 секунд, а записанный PID больше не будет жив; `epx service status` только просматривает её.

### `epx codex-shim <install|status|uninstall|remove>`

На macOS и Linux `epx codex-shim install` создаёт частную обёртку `<EASYPROXY_HOME>/bin/codex` и подключаемый файл `<EASYPROXY_HOME>/codex-shell-env.sh` в разрешённом каталоге EasyProxy. Нативный launcher остаётся там, где его установили brew, npm или fnm, поэтому обновления и возврат к предыдущей версии не требуют повторного оборачивания. В Windows скриптовые launcher по-прежнему оборачиваются на месте, а настоящий `codex.exe` не изменяется. Если доступен только `codex.exe`, используйте `epx service install`.

После настройки PATH для brew/fnm выполните команду активации, напечатанную при установке. Для каталога по умолчанию:

```sh
. "$HOME/.easyproxy/codex-shell-env.sh"
```

Для другого каталога используйте напечатанный путь в кавычках. Повторное подключение удаляет дубликаты частного bin и ставит его первым в PATH. Для будущих оболочек добавьте эту строку самостоятельно после настройки PATH в файле запуска; EasyProxy никогда не редактирует такие файлы. Установка не меняет PATH родительской оболочки. Если обёртка может выполняться, установка успешна даже до активации в текущей оболочке; отказ или неработоспособная обёртка остаются ошибкой. `epx status`, `epx codex-shim status`, `epx doctor` и `epx connect` сообщают **not active** и команду активации, если PATH не выбирает обёртку. Предупреждения connect не меняют код завершения. Псевдонимы, функции и запуск из настольной среды или служб требуют отдельной настройки.

Перед фиксацией установки или repair EasyProxy запускает сохранённый launcher с `--version`,
не запуская сервис. Изменение отклоняется и откатывается, если launcher снова разрешает `codex`
в shim, завершается с ненулевым кодом, работает дольше пяти секунд, оставляет дочерние процессы
или не может быть безопасно проверен и очищен. Поэтому `codex-shim install` не является
безусловной установкой. После отказа переустановите Codex так, чтобы запись в `PATH` указывала на
конкретный исполняемый файл или launcher, и повторите попытку. Если динамический launcher
менеджера команд не проходит эти проверки, используйте вместо него `epx service install`.
Старый Unix shim, установленный на месте, переносится только явной командой `epx codex-shim install`. Записанный нативный launcher восстанавливается без замены уже имеющегося более нового launcher, затем устанавливается частная обёртка. При последующей ошибке установки нативный launcher остаётся восстановленным, а операцию можно повторить. Если записанный launcher отсутствует или не работает, исправьте установку через менеджер пакетов: EasyProxy не выбирает другую установку и не оборачивает заново путь менеджера.

На Unix автоматическое исправление обновляет только частную обёртку: пути менеджера пакетов не перезаписываются, старые shim на месте не переносятся. На Windows после завершённого внешнего обновления, заменившего shim, следующая обычная команда `epx` сохраняет новый стабильный launcher и восстанавливает shim. Меняющийся launcher остаётся нетронутым до повторной попытки. `epx status`, `epx doctor`, `epx codex-shim status`, `epx system codex-cli-update check` и некорректные вызовы его зарезервированного пространства не запускают это исправление. Ошибки приводят к предупреждению без изменения кода завершения запрошенной команды. Ручной вариант: `epx codex-shim install`. Отключение: `codexShimAutoRestore: false` или `EASYPROXY_CODEX_SHIM_AUTO_RESTORE=0` для процесса.

| Подкоманда | Действие |
| --- | --- |
| `install` | Установить shim (или починить, если он устарел). |
| `uninstall` | Удалить частные файлы Unix, сохранив нативный Codex; на Windows восстановить исходный launcher. |
| `remove` | Alias команды `uninstall`. |
| `status` | Показать состояние shim и активность частной обёртки в PATH. |

```bash
epx codex-shim install
epx codex-shim status
epx codex-shim uninstall
```

После удаления на Unix уберите строку подключения из файла запуска оболочки и перезапустите её либо удалите частный bin из PATH. Удаляются только принадлежащие EasyProxy обёртка, файл окружения и состояние; launcher менеджера пакетов остаётся нетронутым. Старый Unix shim на месте освобождается по записанным данным восстановления.

:::note[Окружение токена в Windows]
Новые обёртки для Windows CMD и PowerShell восстанавливают исходное состояние `EASYPROXY_API_AUTH_TOKEN` в вызывающей оболочке после выполнения. Codex и его дочерние процессы по-прежнему могут унаследовать токен.

После обновления EasyProxy пересоздайте существующую обёртку Windows командами `epx codex-shim uninstall`, затем `epx codex-shim install`, чтобы применить это поведение. Обычное обновление не перезаписывает исправную обёртку Windows.
:::

:::tip[Service vs Shim]
Используйте `epx service` для всегда работающего фонового прокси (рекомендуется). Используйте
`epx codex-shim` для лёгкого on-demand запуска без демона — в этом случае прокси стартует только
когда запускается `codex`.
:::

#### Передача токена в Codex

При привязке к адресу, отличному от loopback, внедрённый провайдер содержит `env_key = "EASYPROXY_API_AUTH_TOKEN"`. Эта строка указывает Codex, какую переменную читать, но не создаёт её. Если переменная отсутствует, Codex отказывается начинать запрос (`Missing environment variable: EASYPROXY_API_AUTH_TOKEN`), и запрос не доходит до прокси. Значение хранится в `$EASYPROXY_HOME/service-api-token`; запускающий процесс должен передать его в окружение Codex.

Используйте поддерживаемую обёртку, устанавливаемую командой `epx codex-shim install`. Если в контексте запуска выбирается эта обёртка, она читает файл токена, созданный EasyProxy, и передаёт переменную Codex. При запуске из настольной среды, cron или службы необходимо использовать PATH либо путь к средству запуска, который выбирает обёртку; установка не настраивает эти окружения автоматически. Собственные дочерние процессы Codex также могут унаследовать токен.

Не экспортируйте этот Bearer-токен из файла запуска оболочки и не копируйте его в `config.toml`. Файл `service-api-token` содержит сам токен, а не присваивания вида `NAME=value`, поэтому его нельзя напрямую использовать как `EnvironmentFile=` в systemd.

`EnvironmentFile=` или `EPX_API_TOKEN_FILE` в `easyproxy-proxy.service` настраивает только процесс прокси и никогда не передаётся в независимо запущенный `codex exec`.

На Unix обновления менеджера пакетов сохраняют частную обёртку. Если она не активна, подключите напечатанный файл активации. На Windows или со старым shim на месте обновление, заменяющее launcher, удаляет обёртку; на Windows следующая обычная команда `epx` восстанавливает её (см. выше), но `codex exec`, запущенный до этого, завершается ошибкой. `epx doctor` сообщает об этом состоянии и неактивной обёртке в разделе "Codex env_key launch readiness" (env_key настроен, переменная не задана, обёртка отсутствует или неисправна, файл токена присутствует), приводит инструкции исправления или активации и никогда не выводит токен. Чтение файла токена не входит в контракт внедрённого `env_key`; запускающий процесс должен передать эту переменную.

### `epx tray <install|start|stop|status|uninstall|remove> [--json] [--no-start]`

Установить и управлять Windows tray icon со статусом. Иконка стартует при логине в Windows и даёт
one-click управление прокси. `start` и `stop` управляют только иконкой; самим прокси нужно
управлять из её меню. `--no-start` применяется к `install` и устанавливает tray, не запуская её
немедленно.
Устарело: приложение EasyProxy для рабочего стола предоставляет трей в Windows, macOS и Linux;
`epx tray` остаётся для установок без приложения для рабочего стола.
Когда становится известна новая версия пакета, трей добавляет синюю точку к значку онлайн, предупреждения или офлайн и показывает **Update available**. Локально кэшированный badge проверяется примерно раз в минуту; устаревшие или недоступные результаты убирают точку. Пункт меню открывает панель управления, где можно запустить обновление пакета. Автоматическая установка не выполняется.

## Обновление

`epx update` обновляет сам EasyProxy, а не Codex CLI. Используйте `epx system codex-cli-update check` из [system-команд инспекции](/ru/reference/cli/agents/) для ограниченной read-only проверки provenance настроенного кандидата Codex CLI. Команда не обращается к package registry и не устанавливает обновление.

### `epx update [--tag latest|preview]`

Если EasyProxy установлен через mise, команда завершается с ошибкой до остановки прокси или изменения файлов пакета и показывает `mise upgrade <tool>` с проверенным локальным псевдонимом mise. Проверка обновлений остаётся доступной и сообщает о внешнем управлении. Нечитаемые или противоречивые метаданные владельца mise также запрещают изменения без угадывания имени инструмента, а `--tag preview` никогда не меняет выбранную в mise версию.

В Linux фоновая служба, у которой записанный лаунчер — пакетный лаунчер mise (`<tool>/latest/node_modules/.bin/epx`, а не shim mise), сама следует за `mise upgrade`: примерно через десять секунд после того, как новая версия стабилизируется, она завершает активные запросы и перезапускается на ней, и так же восстанавливается, если mise позже удалит версию, на которой она работала. В macOS, для службы, установленной через shim mise, и для прокси на переднем плане перезапустите её сами после обновления (в macOS сначала `epx service repair`).

Самообновить easyproxy из npm. Стабильные установки используют `@latest`; preview-установки
остаются на `@preview`, если только вы не передадите `--tag latest|preview`. Команда распознаёт
source checkout и предлагает вместо этого `git pull && bun install`, а если у вас уже новейшая
версия для выбранного тега, становится no-op. Для npm-установок до остановки каких-либо процессов
выполняется ограниченная проверка владельца и доступности Unix-кэша. Вложенные символические ссылки
проверяются через `lstat`, но переход по ним не выполняется; в Windows эта Unix-проверка явно
пропускается. При ошибке обновление отменяется, пока трей и прокси ещё работают. Затем перед заменой
файлов работающий прокси останавливается; установленная служба автоматически пересобирается и
запускается заново, а для foreground-установки печатается подсказка `epx start`. В записях обновления
дашборда пути профиля/кэша и значения UID/GID скрываются до сохранения.

```bash
epx update
epx update --tag preview
```

Новые версии становятся доступны, когда
[Release workflow](https://github.com/AquilaXk/easyproxy/actions/workflows/release.yml)
публикует их в npm.

## Жизненный цикл клиента Remote Hub

Используйте `epx connect <url> --pairing-code-stdin`, `epx connect status`, `epx sync` и `epx connect rotate --pairing-code-stdin`. `epx disconnect` офлайн восстанавливает локальное состояние, но не отзывает ключ hub. Пока подключение активно, `epx connect revoke --admin-token-stdin` отзывает сохранённый `apiKeyId`; после отключения используйте **Подключение → API-ключи** на hub. Секреты передаются только через stdin, не argv.
